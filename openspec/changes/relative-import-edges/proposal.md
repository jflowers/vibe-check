## Why

ripwire's `--deps` records a Python relative import as written:
`from . import x` becomes `<inc t="."/>` and `from ..b.api import f` becomes
`<inc t="..b.api"/>`. The adapter's `resolveTarget` (`mapping.go`)
name-resolves a Python target by longest dotted prefix against the module
universe. A leading-dot target matches no prefix, so it is classified as
**external**. As a result, every relative import:

- adds **no directory edge**, so Tarjan SCC in `cycles.go` cannot see a
  cycle that closes through one; and
- is **miscounted in `ExternalOut`**, as if it were a stdlib or third-party
  dependency.

ripwire's own `--arch` Ca/Ce already resolve relative imports, including the
member edge of `from .. import a`. A probe of the pinned build (`1edb6fd`)
shows `pk/b` with `ce=2` for `from .. import a`. So the gap is the
adapter's, not upstream's. Relative imports are idiomatic inside Python
packages, and a structural gate cannot catch a cycle it never derives.

`wide-form-cycle-edges` (draft PR #98) named this gap as a separate
follow-up (its design Non-Goals; its tasks 6.1). This change closes it.

## What Changes

- **Relative base resolution**: for a Python include target with `k` leading
  dots and remainder `R`, the adapter resolves the base relative to the
  importing file's package (its directory). It climbs `k − 1` directories,
  appends `R`'s components, and takes the longest prefix that is a module
  directory, without climbing above the anchor package. A target that
  resolves is an internal edge. A target that climbs above the crawl root,
  or that matches no module at or below its anchor, is **unresolved**
  (dropped, `ambiguity-rate` warning). A relative target is never counted as
  external.
- **Relative member edges**: the member-import light parse
  (`memberimports.go`) also records relative bases (`.`, `..`, `.x`, `..b`)
  verbatim. In the mapping's existing anchored member pass, a relative base
  is resolved against the file's package the same way. So
  `from .. import a` adds an edge to the module `a` when `a` is a module
  directory and ripwire's `--deps` row for the file lists `<inc t=".."/>`.
- **Fixture**: a new `fixturepy/rel_a` ↔ `fixturepy/rel_b` pair whose cycle
  closes only through relative imports. `rel_a` uses a relative base edge
  (`from ..rel_b.api import ...`), and `rel_b` uses a relative member edge
  (`from .. import rel_a`). The Python recordings and goldens are
  re-captured with the same ripwire build as the parent change.
- **Docs**: CHANGELOG notes that Python cycle output can gain cycles and
  `ExternalOut` drops across this change. The FIXTURES and recordings docs
  are updated.

## Impact

- **Modified code**: `internal/ripwireadapter/` — `mapping.go`
  (`resolveTarget` relative branch, plus member-pass resolution of relative
  bases); `memberimports.go` (the regex accepts relative bases); tests in
  `mapping_test.go`, `memberimports_test.go`, `cycles_test.go` and/or
  `assembly_test.go`, and any test that hardcodes the Python module set,
  edges, or line totals; `testdata/python/src/fixturepy/rel_{a,b}/`,
  `testdata/recorded/**`, `testdata/FIXTURES.md`, `testdata/README.md`,
  `golden-notes.md`.
- **Unchanged**: `metrics/` (Layer 1), `modulegraph.schema.json`, verdict
  thresholds, the TypeScript path (its relative targets are already
  path-joined), the Go adapter, the ripwire pin, and Ca/Ce/I/A/D (still
  `--arch` values). No new dependencies.
- **Output**: Python `ModuleGraph.Cycles` can gain cycles that were
  previously missed. Ca/Ce are unchanged. A `diff` across the upgrade
  boundary can report a "new" cycle that existed before, and CHANGELOG MUST
  say so.
- **Base**: branched from `opsx/wide-form-cycle-edges` (PR #98, itself stacked
  on #96). It cannot merge before either, and is rebased onto `main` after
  both merge.
